# 0005. Opt-in links, snapshots and restore

**Status:** Accepted · 2026-11-18

## Context

A library may have fifteen consumers while the developer is testing in three. Installing a dev version
rewrites the consumer's `package.json` and lockfile, and those changes must never reach a commit: the
lockfile would contain `127.0.0.1` tarball URLs that break every other machine and CI.

## Decision

- **Discovery is passive.** dryfit scans configured roots and lists every project that depends on a
  registered library, but does nothing to them.
- **Links are opt-in.** Only a consumer the user explicitly links receives installs. A link persists until
  it is restored. Saved groups ("booking flow") link or restore several consumers at once.
- **Snapshot before first install.** Linking copies the consumer's manifest and lockfile into
  `~/.dryfit/snapshots/<consumer-id>/`. Restore writes them back and runs a clean install, so the repo
  returns byte-for-byte to its pre-link state.
- **Commit guard.** Linking offers to install a git `pre-commit` hook (chained with existing hooks and
  Husky) that rejects staged manifests or lockfiles containing dev versions or the local registry URL.
- **Version coherence warning.** When linked consumers that run together (a federation host and its
  remotes) are on different dev versions of the same library, dryfit warns.

## Consequences

- Nothing happens to a repo the user did not choose. Trust is the feature.
- Snapshots go stale if the user changes dependencies while linked. Restore detects a manifest that changed
  since linking (beyond the dryfit edits) and asks instead of overwriting.

## Amendment · 2026-11-18 (M1 review)

Clarifications from implementing and reviewing M1. They refine the decision without changing it.

- **Only package.json is checked for drift.** Lockfile changes made while linked (`npm update`, a new
  transitive version) are reverted on restore. Separating them from dryfit's own lockfile edits would mean
  re-deriving the dependency tree, and a lockfile change that has no matching manifest change can always be
  regenerated by running the same command again. Clients must say before restoring that the lockfile goes
  back to its pre-link state.
- **Every lockfile the package manager knows is snapshotted**, such as both `package-lock.json` and
  `npm-shrinkwrap.json`. A lockfile the consumer did not have is deleted on restore, and the clean install
  is told not to create one.
- **Consumers are identified by a canonical path**, so `/repos/shop/` and `/repos/shop` share one link and
  one snapshot.
- **A snapshot is reused only while a link refers to the consumer.** A leftover snapshot from an
  interrupted restore is replaced on the next first link, because it predates commits the user has made
  since.
- **Cache paths are deleted only if they resolve strictly inside the consumer.** A configured path such as
  `"."` or `"../.."` is ignored rather than deleting the project or its parents (ADR 0007).
